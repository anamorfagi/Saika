# ANAMORF: реестр фич, первый запуск, компилятор билда

Продолжение `SAIKA_BUILD_PLAN.md`. Здесь — как устроить то, что ты описал:
окно ключей с обучением, экскурсия по моделям, компилятор клиентского билда,
и ответ про pip.

Решения этого захода: движок запечатанной модели — **llama.cpp**; переименование —
**полное** (`anamorf/` → `anamorf/`); компилятор выдаёт **папку + установщик**;
обучение — **затемнение с подсветкой поля**. ANAMORF — система, Сайка — персона.

## 1. Один реестр вместо пяти списков

Всё, что ты описал, — это четыре разных вида одного и того же знания:
«какая есть фича, что ей нужно, что она даёт, где взять ключ».

Сегодня это знание размазано: список pip живёт в `setup/ensure_features.py`,
имена ключей — в `secrets.example.json`, тексты про возможности — в
`#skills-ov` внутри `ui/index.html`, состав установки — в `first_run.py`,
а что вырезать из клиента — вообще нигде.

**Заводим `features.json` — единственный источник правды.**

```jsonc
{
```

Из одного файла получаются:

| что | как |
|---|---|
| Экран ключей при первом запуске | карточки строятся из `title/blurb/group`, панель — из `keys` |
| Обучающая подсветка | `coach[]` — якорь, заголовок, текст. Три шага на ключ, писать один раз |
| Кнопка «Проверить» | `verify` — запрос и разбор ответа. Человек не гадает, правильный ли ключ |
| Экскурсия по моделям | те же `steps/gives/needs`, только для Ollama, LM Studio, GGUF, облака |
| Чекбоксы компилятора | `modules/pip/packs/models` + `stability/risk/devOnly` |
| Что копировать в `app\` | объединение `modules` включённых фич |
| Что ставить в `runtime\` | объединение `pip` включённых фич по `requirements.lock.txt` |
| Что показывать в интерфейсе | `features.on("telegram")` — выключенная фича не рисует свою кнопку |

Один файл правишь — меняются все пять мест сразу. Это же и защита от того, что
у тебя сейчас: `network.py` числился живым в `MODULES.md`, а на него нет ни одной
ссылки. С реестром такое не проходит — «Проверить сборку» видит модуль, который
ни в одной фиче не числится, и ругается.

## 2. pip: как правильно

Три уровня, и ни на одном клиент не запускает pip.

### A. Всё, что в билде — ставится на твоей машине, при сборке

Компилятор берёт `pip` включённых фич, ставит их в `runtime\` по
`requirements.lock.txt` и пакует готовое. У клиента pip не вызывается вообще.

Заодно `requirements.lock.txt` наконец начинает использоваться — сейчас
**его не читает ни один скрипт в проекте**.

### B. Тяжёлое — готовые архивы, не pip

Playwright с Chromium, PySide6 для настольного аватара, Voxtral, DreamPC —
не «pip install у клиента», а **запечатанный архив `pack-<id>-<версия>.zip`**,
который ты собираешь один раз и кладёшь в GitHub Release рядом с установщиком.

Клиент: скачал → сверил sha256 → распаковал в `runtime\packs\<id>\` →
при включении фичи путь добавляется в `sys.path`.

Почему не pip:

- у клиента нет компилятора C++ — любое колесо без готового wheel под его Python упадёт;
- pip тянет зависимости и ломает работающий runtime. **У тебя это уже случалось**:
  T-one откатывал numpy до 1.x, ронял scipy и librosa, и ради этого родился
  `fix_venv.bat` с зашитыми версиями. У клиента чинить это будет некому;
- pip падает по-разному при кривой сети, прокси и заблокированном зеркале —
  а zip качается одним запросом, докачивается и проверяется хешем;
- у всех клиентов одна и та же битовая копия, а не «что pip решил сегодня».

Это ровно тот механизм, который у тебя **уже написан** — `setup/install_llamacpp.py`
ходит в GitHub Releases, выбирает asset, качает, распаковывает, пишет `VERSION.txt`.
Обобщаем его на любые блоки.

### C. Три вызова в рантайме сводим к одной функции

Сейчас `browser_hands.py:109`, `desk_avatar.py:164` и `hotkeys.py:185` зовут
`sys.executable -m pip install`. В замороженном билде `sys.executable` — это
`ANAMORF.exe`, pip там нет, ветка умирает молча.

```python
# anamorf/packs.py
def ensure(feature_id: str) -> bool:
    """Есть ли всё нужное для фичи. Если нет — добыть."""
    if DEV:
        return _pip_install(FEATURES[feature_id].pip)     # как сейчас
    return _download_pack(feature_id)                     # zip из релиза
```

В трёх модулях меняется одна строка на `packs.ensure("browser")`.
`setup/ensure_features.py` становится обёрткой над тем же вызовом.

### Отдельный баг, который выстрелит на всех спавнах

В замороженном билде `sys.executable` — сам exe. Везде, где проект запускает
дочерний Python (воркеры Voxtral, LocalLM, DreamPC, обучение, настольный аватар),
надо звать **`runtime\python.exe`**, а не `sys.executable`. Иначе воркер попытается
запустить приложение вместо интерпретатора. Это надо вычистить одним проходом
до первой сборки.

## 3. Первый запуск

Порядок экранов:

1. **Приветствие** — «ANAMORF работает без единого ключа». Кнопка «Пропустить настройку».
2. **Железо** — что нашли: видеокарта, память, микрофон, колонки. Сразу видно,
   потянет ли машина. Отсюда подбирается профиль качества.
3. **Голос и микрофон** — выбрать устройства, сказать фразу, услышать ответ.
   Это первая точка, где человек понимает, что оно живое.
4. **Подключения** — то, что ты описал. Карточки, у каждой: что даст, где взять,
   поле, «Проверить». Ничего не обязательно.
5. **Готово** — короткий тур по интерфейсу теми же коуч-марками.

Правила обучающих подсказок:

- Затемнение `rgba(0,0,0,.74)` вокруг светящегося окна, окно — с тонким белым
  контуром и мягким ореолом. Реализация — `box-shadow: 0 0 0 9999px` на подсвеченном
  блоке, без второго слоя разметки.
- Максимум **три-четыре шага** на один ключ. Больше человек не читает.
- В каждом шаге ровно одно действие. Всегда есть «Пропустить» и Esc.
- Ссылка ведёт **точно на нужную страницу**, а не на главную сайта
  (`github.com/settings/tokens`, а не `github.com`).
- Кнопка «Проверить» обязательна везде, где ключ можно проверить одним запросом.
  Человек не должен узнавать о неправильном ключе через час, когда что-то не сработало.
- Ключи пишутся в `secrets.json` рядом с данными и **никуда не отправляются**.
  Это надо написать прямо на экране — иначе люди не вставляют токены.

## 4. Модели

**В комплекте:** `gemma-4-e4b`, GGUF Q4_K_M, движок llama.cpp (`llama-server.exe`
уже лежит в `third_party/llamacpp`). ~3.2 ГБ, поднимается без внешних программ,
работает и на процессоре. Это единственная модель, которую человек получает
из коробки, и она обязана отвечать сразу после установки.

**Дальше — четыре двери**, каждая со своей экскурсией:

| дверь | суть | чем платит |
|---|---|---|
| Своя GGUF | положить файл в `models\gguf` — встроенный движок подхватит | место на диске |
| Ollama | `ollama pull` — и модель появилась в списке | ставить стороннюю программу |
| LM Studio | наглядный подбор под свою видеокарту, сервер на 1234 | то же |
| Облако по ключу | 13 провайдеров, часть с бесплатным тиром | интернет, иногда карта |

Для каждой — те же `steps / gives / needs` из реестра. Никаких «настройте
base_url» без объяснения, что это и откуда берётся.

## 5. Компилятор клиентского билда

Панель в твоём билде: слева дерево фич с галочками, справа — итог и кнопки.

**Пресеты:** Минимум · Базовый · Полный · Свой.
Базовый — это ~10 ГБ установщика: ядро, llama.cpp с gemma, GigaAM с черновиком,
Silero и Edge, руки, зрение, аватар в окне.

**Итог считается на лету:** размер установщика, число модулей, число пакетов,
сколько блоков уйдёт в докачку. Отдельной строкой — предупреждения:

- «В сборку добавлен torch» — когда включена любая фича слуха, голоса или зрения.
  +2.9 ГБ. Снимешь их все — уйдёт и он. Это делает цену выбора видимой.
- «Нет ни одного движка слуха» — билд соберётся, микрофон работать не будет.
- «Телеграм и телефон открывают доступ снаружи».
- «Установщик больше 25 ГБ — подумай, что перенести в докачку».

### Как фича на самом деле «вырезается»

Не удалением файлов вручную. Два механизма:

1. **Файлы.** Список `modules` выключенной фичи просто не копируется в `app\`.
2. **Ссылки.** Все входы в фичи идут через один модуль `anamorf/features.py`,
   который читает `build.json` (что включено в этом билде):

```python
if features.on("telegram"):
    from anamorf import messengers          # импорт ленивый, внутри проверки
```

### «Проверить сборку» — это и есть компиляция

Сухой прогон перед реальной сборкой:

- импортировать все выбранные модули — падает импорт, падает и сборка;
- прогрепать выбранные модули на импорты **исключённых** — жёсткая ссылка
  на вырезанное это ошибка сборки, а не сюрприз у клиента;
- проверить, что ни один модуль в `anamorf/` не остался вне реестра фич
  (лечит болезнь «`network.py` числится живым, а его никто не зовёт»);
- проверить, что личные пути автора и секреты не попали в пакет:
  `C:\AI\`, `F:/AI_load_work`, `anamorf.agi@`, `server.token`, `owner.name`;
- собрать итоговый `requirements` и убедиться, что он ставится.

Только после зелёной проверки становятся активны «Собрать папку» и «Установщик».

**Выход:** сначала `build\ANAMORF-0.9.5\` — можно запустить и пощупать своими
руками. Потом одна кнопка — `ANAMORF-Setup-0.9.5.exe` (Inno Setup: ярлык,
автозапуск, удаление через Панель управления). Публикация релиза — отдельная
кнопка, после того как посмотрел глазами.

## 6. Переименование в ANAMORF

Ты выбрал полное. Делать **одним атомарным коммитом и до распила `main.py`** —
иначе переименовывать придётся дважды.

Порядок:

1. `git mv server anamorf`, `git mv workers anamorf_workers` (или оставить `workers`).
2. Автозамена по всем `.py .bat .md .html .json`:
   `from server` → `from anamorf`, `import anamorf` → `import anamorf`,
   `server.` → `anamorf.` (осторожно: `server.host` в конфиге — это другое,
   см. п. 4), `python -m anamorf.main` → `python -m anamorf.main`.
3. Ключи конфига `server.host/port/token` → `app.host/port/token`
   с миграцией в `config.py`: читаем новый ключ, если нет — старый, и пишем новый.
4. `/api` **не трогаем** — это внутренний адрес между сервером и его же
   интерфейсом, ломать `ui/index.html` и WebSocket незачем.
5. Отдельно вычистить строковые упоминания, которые автозамена не поймает:
   белые списки в `setup/ai_doctor.py`, пути в `setup/doctor.py`,
   `setup/known_issues.md`, `AGENTS.md`, `CLAUDE.md`, `.gitattributes`.
6. Прогнать `tests/` и smoke-import всех модулей. Запустить и поговорить с ней.

Витрина: `ANAMORF.exe`, заголовок окна `ANAMORF`, папка установки `ANAMORF\`.
**Сайка остаётся именем персоны** — так она себя называет, так к ней обращаются,
так подписаны её реплики. Система и персона — разные слои, и это честно:
человек ставит ANAMORF, а разговаривает с Сайкой.

## 7. Что уходит только в твой билд

По твоему решению — целиком дев-профиль, `devOnly: true`:

- дорожная карта проекта (`devboard`);
- git-панель (`git_sync`);
- обучение характера, LoRA, датасеты, Hugging Face (`dataset_hub`, `train_manager`);
- **мост в Unreal Engine и управление моделью/интерфейсом в UE**;
- стенды и замеры (`hear_bench`, бенчмарки из `tools/`);
- чтение собственного исходника (`self_read`);
- файловый пульт (`knobs`);
- сам компилятор билда.

Удаляем совсем (ты согласился): `network.py` — ноль ссылок во всём репозитории;
мёртвая половина `git_sync.py` — `smart_pull`, `incoming`, `conflict_files`,
`resolve_conflict`, `finish_merge`, `abort_merge`.

## 8. Порядок работ, обновлённый

1. **Гигиена и секреты** — токены из git, `git gc`, удалить мёртвый код,
   вычистить `sys.executable` из спавнов, убрать три runtime-pip.
2. **Переименование в ANAMORF** — одним коммитом, пока код не распилен.
3. **`features.json` + `anamorf/features.py`** — реестр и `features.on()`.
   Разметить все существующие модули по фичам. Это самый большой кусок ручной
   работы и одновременно самый ценный: после него и билд, и первый запуск,
   и интерфейс строятся из одного файла.
4. **`packs.ensure()`** — докачиваемые блоки вместо pip.
5. **Раскладка билда** — `runtime\` + `app\` + тонкий `ANAMORF.exe` + pywebview.
6. **Компилятор** — сухая проверка, папка, установщик.
7. **Апдейтер и каналы** — `manifest.json`, GitHub Actions, откат.
8. **Первый запуск** — экраны и коуч-марки из реестра.
9. **Интерфейс** — Graphite, кольцо, единая правая панель.
10. **Тесты, CI, распил `main.py`**.

Пункт 3 — точка, после которой всё остальное становится механикой.
До него любая сборка будет ручной вознёй со списками файлов.
