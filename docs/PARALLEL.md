# PARALLEL.md — правила параллельной работы над проектом

> Заведено 2026-07-28. Для владельца И для любого ИИ-чата, который правит
> C:\Saika. Причина: файлы пишутся ЦЕЛИКОМ, слияния нет — побеждает
> последний записавший. Реальные инциденты уже были: reset съел
> незакоммиченные правки рабочего ПК (2026-07-27), работающая Сайка
> затирала правки конфигов (починено слиянием в config.py — но только для
> конфигов, код так не защищён).

## Кто пишет в проект (все три — одновременно)

1. **ИИ-чаты** (Claude/Cowork и другие) — правят код. Каждый держит СВОЮ
   копию файла и записывает её целиком поверх диска.
2. **Работающая Сайка** — пишет config.json / config.local.json (слиянием),
   devboard.json, data/, logs/, .setup_state.json.
3. **git** — приносит чужие правки при pull и УНОСИТ незакоммиченные при
   reset. Это не писатель, это стихия: страховка и угроза одновременно.

## Правила для владельца

1. **Один файл — один чат.** Параллельные чаты допустимы только по разным
   зонам. Готовые зоны:
   - `server/` (кроме `server/llm/`) — логика сервера;
   - `server/llm/` — модели и движки;
   - `ui/` — интерфейс;
   - `HandsPC/` — руки-сервис;
   - `setup/`, `tools/` — установка и утилиты;
   - `workshop/`, документация (*.md) — безопасна почти всегда.
   Говори каждому чату его зону ПЕРВЫМ сообщением: «работаешь только в ui/».
2. **finish_day.bat перед параллелью и в конце дня.** Git-коммит превращает
   худший сценарий из «работа пропала» в «откатил за секунду». Незакоммиченное
   живёт до первого reset/pull.
3. **Конфиги руками — только при остановленной Сайке.** Работающий процесс
   пишет их из своей памяти; слияние защищает НОВЫЕ ключи, но значения
   известных ему ключей он перепишет своими.
4. **Не проси два чата «доделать одно и то же».** Даже в разных зонах одна
   задача у двоих = два разных решения, которые сойдутся конфликтом.

## Правила для ИИ-чата (читать как обязательные)

1. **Спроси/определи свою зону.** Если владелец зону не назвал, а работа
   выходит за одну папку — спроси, нет ли параллельного чата.
2. **Свежая копия перед правкой.** Перед КАЖДОЙ правкой файла забирай его
   с диска заново (re-stage), а не правь копию, взятую час назад. Долгая
   пауза (>30 мин) = копия протухла.
3. **Предохранитель времени изменения.** При записи взводи mtime-guard
   (у моста Cowork — expectedMtimeMs из свежего stage): файл изменился с
   момента забора → отказ от записи → перезабрать, наложить правку заново.
   Слепой force — только если владелец явно сказал «затри».
4. **Не трогай чужое.** config.local.json — машинный, его пишет Сайка;
   devboard.json — правится только через server/devboard.py; data/ и logs/ —
   владения работающего процесса.
5. **Проверяй синтаксис перед записью** (ast.parse / node --check) — сервер
   перезапускается руками, битый файл обнаружат не сразу.
6. **Правки server/** требуют перезапуска Сайки, ui/** — только F5,
   config llamacpp.* — движок перезапустится сам по отпечатку. Говори
   владельцу, что из этого нужно.
7. **Крупный заход — запись в дев-доску** (server/devboard.py: add_item),
   а не только в переписку: следующий чат начинает с чистого листа.

## Как выглядит затирание (чтобы узнать его в лицо)

- «Я же это чинил вчера, почему опять сломано» — правка затёрта чужой
  записью или reset'ом.
- Файл на диске новее, чем ждал чат, а записалось старое — чат писал
  протухшую копию без mtime-guard.
- Настройка «сама» вернулась к старому значению при работающей Сайке —
  значение известного ей ключа переписано из её памяти (это не баг
  слияния: свои ключи процесс законно пишет сам).

## Минимальный чек-лист параллельного дня

```
1. finish_day.bat                      # точка отката
2. чат №1: «твоя зона — server/llm/»   # зоны названы явно
   чат №2: «твоя зона — ui/»
3. ...работа...
4. finish_day.bat                      # день закреплён в git
```
