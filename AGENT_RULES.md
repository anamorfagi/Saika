# ПРАВИЛА РАБОТЫ С ЭТОЙ СИСТЕМОЙ (для любого ИИ-помощника)

> Записано 27.08.2026 после дня, в котором помощник трижды попросил
> владельца перезапустить приложение — там, где перезапуск не был нужен
> вообще, а на третий раз ещё и сломал механизм перезапуска.
> Владелец, дословно: «делай так, чтобы я больше не слышал о том, чтобы
> перезапустить прогу». Это не пожелание. Это требование к конструкции.

## ГЛАВНОЕ ПРАВИЛО

**Не просить человека перезапускать приложение. Никогда.**
Просьба нажать кнопку = признание, что живого обновления нет. Если правка
не доезжает — чинится механизм доставки, а не человек дёргается.

## ЧТО У ПОМОЩНИКА ЕСТЬ (проверено боем)

| Инструмент | Что может | Чего НЕ может |
|---|---|---|
| `device_bash` | Читать/писать/править ЛЮБЫЕ файлы в подключённых папках (`Saika`, `Downloads`, `Loading`). Python, grep, sed | **Запускать Windows-процессы.** Это Linux-VM: нет `cmd.exe`, нет `.exe`, нет WSL-interop |
| Канал команд `data/eval_ctl.json` | `ping`, `cfg`, `runpy`, `restart`, `say`, `tts`, `vp`, `bench` | Работает ТОЛЬКО пока жив сервер И жив интерфейс (читается в опросе `status()`) |
| Живая прививка `anamorf/live.py` | Менять тела функций, классы, добавлять маршруты — **на работающем процессе, без перезапуска** | Верхний уровень `main.py` (константы, импорты), запуск новых потоков |
| Авто-вотчер `.py` (поток `_ui_watch`/hot) | Сам замечает правку файла и зовёт прививку. Работает без интерфейса | — |
| Вотчер `ui/*.html` | Шлёт `ui_reload` во вкладку — интерфейс обновляется сам | Мёртвая вкладка (упавший JS) сигнал не примет |
| `runpy` через канал | Запускать python-скрипты питоном приложения (GPU, HF, torch) | Только при живом сервере |
| Blender-мост | Выполнять python на Windows → в т.ч. запустить `.exe` | Работает, только если Blender ОТКРЫТ |
| Chrome-мост | Открывать страницы, читать DOM, кликать | Запускать процессы — нет |

**Вывод:** пока приложение живо — помощник может почти всё, включая
обновление кода без перезапуска. Как только оно упало — у помощника
НОЛЬ способов поднять его самому. Значит падать оно не должно, а если
упало — поднимать обязан внешний сторож.

## ПОРЯДОК ДЕЙСТВИЙ ПРИ ЛЮБОЙ ПРАВКЕ

1. Правка `anamorf/*.py` → сохранить файл → **ждать**. Вотчер сам
   привьёт её на живой процесс (в логе: «Живая правка …»). Перезапуск НЕ
   нужен.
2. Правка `ui/*.html` → сохранить → вотчер шлёт `ui_reload`, вкладка
   обновится сама.
3. Перед сохранением JS/HTML — **проверять синтаксис** (`node --check`
   или разбор `<script>`), иначе падает вкладка, а вместе с ней канал
   команд, и связи с системой не остаётся.
4. Перед сохранением `.py` — `ast.parse`. Всегда.
5. Правки верхнего уровня `main.py` (новые константы, импорты, запуск
   потоков) прививкой НЕ доедут — их планировать так, чтобы они
   применялись при ближайшем штатном старте, а не требовать рестарта.

## ЧЕГО НЕ ДЕЛАТЬ (проверено на живом билде)

- **Не трогать механизм перезапуска.** Сервер — дочерний процесс лаунчера
  и привязан к окну. `os.execv` рвёт эту связь: окно есть, сервера нет.
  Лаунчер поднимает сервер ТОЛЬКО по коду выхода 7 (`launcher/main.py`,
  `RESTART_CODE`); при любом другом коде его надзорный поток завершается
  и больше не следит.
- **Не полагаться на канал команд как на единственную связь** — он живёт
  внутри опроса интерфейса.
- **Не собирать билд поверх запущенного приложения** без учёта занятых
  файлов (`build_client.py` умеет пропускать занятое).
- **Не просить владельца ничего перезапускать, закрывать, кликать.**

## СЛОИ БЕСШОВНОСТИ (цель архитектуры)

1. **Горячая замена кода** — есть (`live.py`), снимает ~99% перезапусков.
2. **Проверка перед прививкой** — компиляция/импорт патча в отдельном
   процессе, в живой попадает только прошедшее проверку. ← делать
3. **Сторож вне процесса** — `watchdog_saika.pyw`: стучится на порт,
   поднимает `ANAMORF.exe`, если тишина. Стартует из `main.py`
   (`_spawn_watchdog`), переживает падение приложения. ← сделано, ждёт
   первого живого старта
4. **A/B-слот с автооткатом** — `app/` и `app.new/`, не поднялось за N
   секунд → сторож возвращает прежний слот. ← делать
5. **Уведомление вместо события** — человек видит «обновлено», а не
   «перезапусти».

## ЕСЛИ ВСЁ-ТАКИ УПАЛО

Сначала честно проверить, а не гадать:
- лог `data/logs/server.log` — растёт ли (`stat -c %s`);
- `data/eval_ctl_ack.json` — отвечает ли канал на `ping`;
- `data/logs/launcher.log` — что сказал лаунчер;
- `data/logs/watchdog.log` — видел ли сторож падение.

Если сторож на посту — он поднимет сам. Если нет — это дефект
конструкции, чинить его, а не перекладывать на человека.

## КОДИРОВКА И ИМЕНА — ТОЛЬКО ЛАТИНИЦА

Кириллица в ИМЕНАХ файлов/папок/скриптов и в путях на Windows ломается:
.bat/.cmd в OEM-кодировке (cp866) видят кракозябры вместо кириллицы и
падают; пути с русскими буквами рвут запуск exe и подпроцессов.

ПРАВИЛО:
- Имена файлов, папок, .bat/.cmd, ключей — ТОЛЬКО латиницей.
- Внутри .bat комментарии и echo — латиницей (или транслит), не кириллица.
- Python-строки в UTF-8 файлах — кириллица можно, имена переменных — латиница.
- Уже наступал на это много раз. Не повторять.

## Грабли, на которые уже наступали

`docs/ГРАБЛИ_СЛУХА.md` — двенадцать ошибок, каждая стоила владельцу
времени. Прочитать ПЕРЕД тем, как трогать слух, нарезку, ручки настроек
или живую правку кода.

Три из них повторялись чаще прочих, поэтому коротко здесь:

1. **Ручка не читается там, где ты её ставишь.** Перед подбором любого
   порога — grep по имени ключа в коде. `getcfg` в кавычках (`'9'`)
   означает строку, а строку сравнивают с числом и молча падают.
2. **Настройка читается один раз при рождении объекта.** Живой объект
   останется со старым значением. Делать свойством — и обязательно с
   сеттером.
3. **Проверять правку класса запуском, а не `ast.parse`.** Вставка
   метода в середину `__init__` рвёт конструктор пополам, синтаксис при
   этом остаётся валидным. Собрать класс отдельно и создать экземпляр.

И общее: **прогон, который никуда не записан, — не измерение.** Замер
кладёт строку в `logs/bench_hear.jsonl` вместе со снимком всех ручек.
